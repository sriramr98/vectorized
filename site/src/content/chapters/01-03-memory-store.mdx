## The problem

A TCP server can accept bytes, and RESP can give those bytes structure. But neither answers the question that matters to a database client: **what happens to my value after `SET` returns?**

The first storage layer is deliberately small. It gives us a place to define semantics before durability, sorted tables, and vector indexes make the system harder to reason about.

<div class="flow-strip">
  <span>CLIENT</span><i>→</i><span>RESP</span><i>→</i><span class="hot">MEMORY STORE</span><i>→</i><span>RESPONSE</span>
</div>

## Establish the invariant

The store accepts byte slices, but it must not retain ownership of memory that a caller can later mutate. Likewise, a value returned by `Get` must not allow a client to mutate the database behind its lock.

<div class="invariant-callout">
  <span>INVARIANT 03</span>
  <p>Callers and the store never share mutable value bytes.</p>
</div>

That decision allows the protocol, storage engine, and future WAL to evolve independently without invisible aliasing between layers.

## Prove the behavior

The valuable test is not merely “set then get.” It mutates the input after `Set` and mutates the result after `Get`. That test preserves the ownership boundary when the in-memory map is eventually replaced by an LSM-tree engine.

```bash
go test -race ./db
```

  <div><span>01</span><strong>Isolation</strong><p>Input and returned slices cannot mutate stored state.</p></div>

## What remains broken

The store loses everything when the process exits. The next chapter will introduce a write-ahead log and define precisely when Vectorized may acknowledge a mutation.
